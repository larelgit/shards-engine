# Progress on the spec

Check against [engine-tz.md](engine-tz.md): what from "What to do" and "Done when" of each module E1–E11 is already in place,
where it lives and how it is verified. Status as of 17 October 2026: all five phases, A–E, are built (see "Phases"). Phase E covers stylised
materials, foliage, effects and decals, budgets and the performance test, Steam, the Windows build, the crash report,
screenshots without a window and the internal 3D resolution. With it comes the tail of E11: a replay from a snapshot together with content edits and
levels placed by id, an agent player on the stand, and scenarios for the modules of phase E. What is still open is what cannot be checked here (a clean
machine, a second Steam account, 60 FPS on the target PC — the maintainer has these), streaming of tile geometry for physics (not needed yet,
see "Known limitations") and mini-dumps with a window for the player beyond the crash report (E10.7: this stage is postponed by the owner's decision).
CI on GitHub (`.github/workflows/ci.yml`) runs on every pull request, every push to `main`, release tags `v*` and by hand (jobs `test`, `clippy`, `template`, `headless-cli` with a
three-minute soak on a live stand, and `replays-window`); `test` and `template` run their tests with cargo-nextest (profile `ci`: a test that passes only on a retry fails the run). `soak.yml` plays the half hour of E7 every night, `nightly.yml` runs the long checks (every reference replay with heavy mode, 100000 worldgen seeds, the GPU tests on a software driver, the performance tests) and opens an issue labelled `nightly` when one fails, `cross.yml` verifies the reference replays on Windows and Ubuntu 22.04 every week, and `record-replays.yml`
records the reference replays on Linux on demand.

Statuses:

- ✅ done: the code is in the repository, and there is a test, a scenario or a command that checks it;
- 🟡 partly: it works, but not all of the spec item is done or checked (the "where" column says what is missing);
- ⏳ ahead: the phase (A–E) in which the item is done. There is no code for it yet.

Rules for this file: set the status from the code and the tests, not from intent. If an item cannot be checked here, say so.
When you change a module, change its section too.

## Known limitations and deferred work

What does not work the way you might expect, and what is deliberately deferred:

- **`fuzz` and `soak` do not kick a client and let it rejoin.** `net_kick` ends a client's link, but a rejoin is something the client's own process does (`--join`, or a
  stand's `stand_client` in a test): no tool makes a client join again, so a run cannot follow a kick with a rejoin. Chaos is single-game only (`shards fuzz`); the stand soak
  stays as it was. A tool that lets a stand member rejoin would close this.

- **Outside the region, `path_to` is local.** Outside the loaded region (and for a body that the navmesh does not serve), `path_to` and
  `move_to path=true` use a local grid A* (cell 0.5 m, search in a limited area, no farther than 80 m by default), and
  `clearance` uses only physics rays.
- **The navmesh is per body class.** Tiles are baked for `agent` from `nav` (by default, the sandbox skeleton's body) and for each
  class `bodies` (in the sandbox, `large` is the guard's body); routes of any walker (an NPC and its direct line to the target in sight, `move_to
  path=true`, `path_to`, `clearance`, `nav_path`) follow the tightest class that serves all of its body (not narrower, not
  lower, a step, climbing over and a slope no worse, the same swimming depth), with its own body; a body that none
  of the classes serves plans on the local grid, so a tall NPC needs its own class in `bodies` with its height, otherwise its routes
  are longer and are searched in a limited area. Each class is one more bake of all tiles and one more navmesh of the region in
  memory and on load; `nav_overlay` draws only the `agent` navmesh. Bodies have no jump and no ladders: `navlink` is good for
  going down, and for going up within climbing over and a step. Cutting (`solids`, applied after baking) can only switch cells off, not add steps.
  Avoiding bodies is local (a fan of velocities over the `horizon`): it does not look for places around the target, so a pack that arrives
  in single file stands in a second row behind the first, not in a circle (the director hands out places by the roles of those waiting). The navmesh must
  be baked after a tile is edited
  (`--bake-nav`), otherwise the content names a stale file, and the region bakes the tile when it loads.
- **Physics uses a grid broad phase (was: a linear scan).** From S1, a query checks only the colliders in its own cells of the grid over the
  ground (levels 2, 16, 128 and 1024 m), in `ColliderId` order and with the answers of the full scan (E2.1). What is left: the grid is flat
  (x, z), so colliders that stand one above another (the floors of a dungeon) share cells and are checked together; a ray that would have to read
  more cells than the scan costs (across half the region and beyond: 300 m on 8×8 tiles of 96 m — 1.1 times
  faster than the scan), and a world with fewer than 32 colliders uses the scan; a long ray of sight or a projectile across the whole region is still
  O(n). Measurement: with 2644 colliders, eight body queries take 16 µs instead of 50, with 212 they take the same as the scan; a full-size region
  loads in 0.6 s instead of 3.9, the tick takes 0.5 ms instead of 0.9 (`broad_phase_timing`, `reference96`).
- **Levels from Blender are checked on one export from one version.** The pipeline is checked on a real export from Blender 5.2.2 LTS
  (`tools/blender/outpost_level.py`, files and tests in `crates/shards_level/tests/level/`); other versions of the exporter have not
  been tried. `ruin.gltf` of the sandbox and the template is now also a Blender export (glTF Embedded, `tools/blender/ruin_tile.py`). Compressed
  meshes (Draco, meshopt in both variants, `EXT_` and `KHR_`, — all checked on a Blender export; quantisation, which Blender
  does not write) are not read, and Bevy does not draw them either.
  An edit to the tile file itself, made in a running game, is not checked again by the content (the file is not a content file): if it is broken on the fly, it
  shows in the journal when the loader reads it, a region change that uses it is refused, and `shards content check`
  reads the file again.
- **Navigation links in the reachability check are taken on the author's word.** The generator takes navlinks from the tile's `navlinks` (it does not open
  level files), and `content check` only matches the names against the markers of the file. Which `links` group a navlink starts from and which group it leads to
  is not checked against the ground (as the `links` themselves are not), and the navmesh may not take a link that the body cannot make (a climb above
  climbing over, a jump: `nav_info` names the reason). There are no tiles with navlinks in the sandbox or the template yet: the regions and their reports
  stay as they were.
- **Only the tile pictures stream.** The region's geometry for physics is built in full when the region loads; by distance, only the visual tile scenes are loaded and unloaded
  (`stream.rs`, only with a window). Streaming of geometry for physics
  is not needed now: a full-size region from the spec (`reference96`: 8×8 tiles of 96 m, about 1900 colliders, a navmesh of both
  body classes with 2.3 million nodes each) loads in release in 0.61 s against 10–15 s in the spec, the tick takes 0.46–0.63 ms against 16.7 ms, the colliders
  take less than a megabyte; it will be needed if there are an order of magnitude more colliders or if tiles start loading from disk during the game.
  **Foliage does not stream either:** it is scattered over all tiles when the region loads, and no more than 10 000
  mesh entities of a definition per tile; the undergrowth density (0.4 bunches per m²) on 64 tiles of 96 m would give about 470 000
  mesh entities, so `expanse` has grass twenty times sparser (about 31 600 mesh entities with all levels of detail).
  Dense grass on a full-size region waits for scattering by distance to the players, as the tile pictures do. The offset curve
  of the hero's actions is baked from a clip (`--bake-motion`, `motion_bake`), but only the forward movement of the root bone: vertical and sideways
  drift is not taken (the baking names the sideways drift in its report). The offset of enemy actions is still set by numbers in the content.
- **The region in a save.** The `region` section (version 2) stores the manifest, and the world is built from it, but the tiles, rooms and prefabs
  that it names must always stay in the content: without them the load is refused (a `region` migration is needed that will replace them
  in the manifest). Saves of version 1 do not keep the manifest: they are generated again, and after a change to the generator they are refused until
  they are saved again on the old content. The `RegionRef` of the `position` section is an id and a seed, without a hash: a character from the world of an older
  generator, on a world generated again with the same seed, is placed at the old coordinates.
- **Animation.** Layers (upper and lower body) exist, but the layer mask is built from the model's bones when the player is bound, and only by name
  rather than by the file's hierarchy: a layer bone that the model lacks leaves the action with the movement clip (a warning).
  The bridge picks up clips of the shared skeleton. The repository has one
  model: a low-poly humanoid from Blender (`tools/blender/humanoid.py`), which every character in the sandbox and the template uses;
  in the sandbox, drinking from the flask uses a hand on the upper layer (the `drink` clip is in the second file); the template has no flask; there is no leg IK.
- **Input.** Rebinding is stored in the player's settings (E8.6); `input.ron` is only carried over. The gamepad has not been checked on a
  real device. Telegraph symbols wider than ASCII (`⚠`) are drawn with strokes or with a suitable font
  (`ThreatHud::font`); without a font, ASCII is used.
- **Attack zones are flat.** `hit_zones` and the hint "step out to N m" count the zone's footprint on the ground (a sphere as a circle, a cone
  as a sector). For "leave the zone" this is enough; only the strike itself takes a jump over a low line into account.
- **A broken dictionary in a content file drops all its definitions.** A definition that does not fit its type is its own
  error (file, line and column, kind, id), and the file's other definitions still load. But a syntax error, an empty id,
  a repeated id in the file, or an unusable id breaks the dictionary `{ "id": (…) }` itself: such a file adds nothing to the database, and next come
  errors "unknown action …" from the files that refer to its definitions. The cause is the first line of the list. An edit to a
  file where at least one definition is broken is not applied as a whole: the previous version stays in force for all of its definitions.
- **Replays are tied to the build and the content.** A change to a number in the content or in the gameplay makes a replay diverge at the next check
  (`DIVERGED at tick 60`); the references are recorded again (`record_reference_replays`). A replay can start from a snapshot: the region,
  content edits and levels placed by id go into the snapshot; a level that the game placed itself, not by id, and geometry
  that a content edit rebuilt outside entities with `AiId` do not (the load is refused at the `static_colliders` check).
  A snapshot taken before `PlacedLevels`, while a level placed by id was in place, now does not load (the level is removed, and the check
  `levels` refuses): take it again. A snapshot and a replay from another minor version of the engine are not accepted (`force` skips the check): after the version went up
  to `0.3`, the reference `tests/replays/snapshot.json` is recorded again.
- **Screenshots without a window need a GPU** (`--offscreen`) or software rendering: WARP is checked on Windows, Mesa lavapipe on Linux
  has not been checked. There are no screenshots in CI: the job is not added.
- **The CI job `replays-window` is optional** (`continue-on-error`) until it proves stable on the
  runners. The other four jobs are required.
- **Tags are not set.** The maintainer sets `v0.1.0` (commit `e90193d`), `v0.2.0` and `v0.3.0`; the version in `Cargo.toml` stays
  `0.2.0` until the maintainer releases `0.3.0` (the phase B entries are already in `CHANGELOG.md` under `0.3.0`). While there are no tags, the game pins
  the engine to a commit (`rev = "…"`).
- **Joining a session: there is a cookie, but no rate limit per address.** From S2, a peer is admitted only by a datagram with a cookie that the host
  gave this address and this session for a knock no more than a minute ago (`shards_net::cookie`): a forged address does not take up a place in the table of strangers
  and costs the host nothing except the reply to the knock (no more than the knock itself, so the host does not become an amplifying reflector either).
  The earlier limits stay: `Hello`, `Ready` and `Bye` from an admitted peer in a row are not rate-limited (the limits that still hold: the budget
  for parsing per poll, the join window `6 × timeout_secs`, the time to forget a peer that left — 10 s without confirmations, a ceiling of 5 minutes, and
  `max_strangers`); a peer that knocks again and again gets a cookie and is admitted again; a session on LAN runs without an identity
  check. **Known limit, in narrow form:** whoever owns many real addresses (or ports of one address: `PeerId` —
  a hash of the address with the port, there is no limit on IP) and knocks and sends without stopping from each one, can still delay, or even break,
  the join of a player whose `Hello` comes in parts, or who arrived in one datagram on the same tick as a batch of such datagrams; now this
  costs him a "knock — reply" round trip from each address. A game of the previous build (protocol 1) gets a refusal in its own protocol; a game
  of this build gets no reply to its knock from a host of the previous build, and after `timeout_secs` it says what that may mean.
- **Content does not change during a session (a ban, not a broadcast).** The content hash is checked on join; during a session the content is not sent.
  From S2 a change that would split the machines is not allowed through: while the host has a client past `Hello` (or a client in the session),
  `content_reload`, `content_apply` and `level_reload` are refused with a reason (`refused: a content reload during a co-op session
  would desync its 2 clients; do it once they have left, or after net_end`), and a file that changed on disk waits and is applied by itself
  when no clients are left or the session has ended (the journal says so once). Earlier, the first
  half-hour `shards soak` ended this way: the region file was changed in the middle of the game, and the client could not take the regenerated world. There is no broadcast of changes: the host
  would have to send definitions, level files and baked navigation, and change them for everyone on one tick, and the world built
  around the old content would have to be built again. Content is edited between sessions, as before, but now without a desync;
  `nav_bake` (writing navigation files) is not covered by the ban.
- **Saves in co-op: what is not done.** From S2 the client asks the host for its character itself (`save_game what=character`:
  the host takes the body that the player plays with on the host and sends it, the client writes the named slot), and a character up to 1 MB goes in parts
  after `Hello`. Still to do: the tool's answer on the client is "requested", not "saved" (the file is written when the host's answer arrives;
  they wait for it in the journal, `step --until "journal:saved (save_game"`); the host does not answer more often than once a second; a character over 1 MB no
  host will accept, and the client does not write one from the host; from the host to the client a character goes as one reliable message (the channel itself cuts it into
  1 KB pieces, limit 16 MB). The default slot is `slot1`; on a client, it is named after the player. Branches with a replay being played
  (`replay_playing`) in the host's routing are not covered by tests.
- **UI: what is missing.** The key-binding screen does not change the axes (stick, `WASD`); only `settings_set` does. The loading picture is not visible during a
  region change that ends inside one call (there is no frame between them). The sandbox has no main menu (it is in the template).
  Drawing is checked by a test without a GPU (nodes, theme, AccessKit labels) and by an `--offscreen` screenshot, not by a real screen reader;
  the menus have not been tested with a real gamepad.
- **The reference replays are recorded again; across OSes they are checked on one machine only.** The earlier ones (recorded in `fb78b42` on 14 October)
  diverged on any OS: the content hash of the sandbox and the template has changed since then (phases C and D, the E10.1 looks, the E10.2 foliage,
